# Co-simulation contract v1.1

**Status:** authoritative — the single source of truth for all game↔backend traffic
(ROADMAP §5, Phase 2). Backends and the game implement THIS document; when code
and spec disagree, the spec wins and the code is fixed. JSON Schemas live in
[schemas/](schemas/); shared fixture topologies in
[../../tests/contract/fixtures/](../../tests/contract/fixtures/).

Every backend (rtpowerflow "power", rtheatflow "heat", rtwaterflow "water" from
Phase 5) exposes the same surface under `/gb/*`, enabled by the backend's
`*_EXTERNAL_CLOCK=true` puppet mode.

## 0. Ground rules

1. **The game owns time.** Backends never self-advance in puppet mode.
2. **Divergence is data, never an HTTP error.** A failed solve returns
   `status: "failed"` with HTTP 200; the game maps it to gameplay events.
3. **Idempotent stepping.** Re-sending the last step `t` returns the cached
   result without re-solving. Any `t` other than `last_t` or `last_t + 1`
   is an out-of-order error (the one 4xx in the step path).
4. **Contract handshake before anything else**; the game refuses to run on a
   major-version mismatch.
5. **JIT warmup at reset**: `/gb/net/reset` fires one throwaway solve so numba
   compilation (~3 s) never lands on a live step (ADR-003).

## 1. Transports

- **Control plane — HTTP**: `/gb/version`, `/gb/net/reset`, `/gb/net/patch`,
  `/gb/result/latest`, plus the backend's existing `/health`.
- **Step channel — WebSocket `/gb/ws`** (ADR-003: ~7× less overhead): one text
  frame in = one step request (§4 body, same JSON as the HTTP variant), one text
  frame out = the step result. Strictly sequential — the client keeps at most
  one request in flight. `POST /gb/step` remains as the debugging fallback and
  MUST behave identically.

## 2. Handshake

`GET /gb/version` →

```json
{"contract": "1.0", "backend": "netzsim", "api": "0.2.0",
 "solver": "pandapower 3.5.4", "external_clock": true}
```

`contract` is MAJOR.MINOR: the game requires identical MAJOR and
game-minor ≤ backend-minor.

## 3. Topology

### 3.1 `POST /gb/net/reset`

Body — the **topology document** ([schemas/topology.schema.json](schemas/topology.schema.json)):

```json
{
  "contract": "1.0",
  "network_kind": "power",
  "name": "contract_power_fixture",
  "steps_per_day": 96,
  "native": { … },
  "zones": [{"id": "z0", "node": "b1"}],
  "devices": [{"id": "slack", "kind": "slack", "node": "b0", "params": {"vm_pu": 1.0}}]
}
```

- **`native`** is the backend-family-specific network description — the
  established, validated input contract of each backend, verbatim:
  - power: netzsim's five-doc `GridInputs` shape
    (`grid_structure`, `lines`, `load`, `generation`, `substation`) — loads and
    generation MAY be present in `native` for fixed background elements; all
    game-driven elements come from `zones`/`devices`.
  - heat: rtheatflow's five-file bundle
    (`network_structure`, `pipes`, `consumers`, `producers`, `weather`).
  The game builds `native` through per-network builders; the uniform layer is
  everything else in this document. Profile arrays inside `native` MUST have
  exactly `steps_per_day` entries; game-driven rows are all-zero placeholders.
- **`zones`** — supply zones (ROADMAP §2.4): the aggregation points whose
  demand the game sends every step. Backend maps each zone onto one consumer
  element at `node` (power: a load row; heat: a consumer by name in `native`
  via `"consumer"` instead of `"node"`).
- **`devices`** — game-controlled elements. v1 kinds:

  | kind | networks | params | setpoint (§4) | result fields |
  |---|---|---|---|---|
  | `slack` | all | power: `vm_pu`; heat: maps onto the bundle's slack producer | — | `p_kw` (import +) |
  | `generator` | power | `p_max_kw` | `p_kw` ≥ 0 | `p_kw` |
  | `pv`, `wind` | power | `p_rated_kw` | `p_kw` (game computes from weather) | `p_kw` |
  | `coupling_load` | power | — | via `coupling_in` | `p_kw` |
  | `chp` | heat | `pq_ratio` (default 0.5) | `q_kw` heat dispatch | `q_kw`, coupling `p_el_kw` (production, ≤ 0 as load convention: **negative = feeds the grid**) |
  | `heat_pump` | heat | `eta_g`, `t_cold_source` | `q_kw` | `q_kw`, `cop`, coupling `p_el_kw` > 0 (draws) |
  | `boiler` | heat | `eta` | `q_kw` | `q_kw`, `p_fuel_kw` |
  | `battery` | power | `e_kwh`, `p_max_kw` | `p_kw` signed: **+ discharges into the grid, − charges** (clamped to `p_max_kw` and SoC energy bounds over `dt_s`; clamping → `clamped` violation) | `output_kw` (realized, signed), `soc` ∈ [0,1] |
  | `storage_heat` | heat | `e_kwh`, `p_max_kw` | `q_kw` signed since 1.1: **+ discharges into the net, − charges** (mapped onto the backend's storage modes; clamped to `p_max_kw`/SoC by its machinery) | `output_kw` (realized, signed as the setpoint), `soc` ∈ [0,1] |
  | `well` | water | `rated_m3_h` | `yield_factor` ∈ [0,1] (game-driven drought/aquifer state; scales the well's available yield) | `detail.q_m3h` |
  | `water_pump` | water | `rated_m3_h`, `head_m`, `eta` (default 0.6) | `enabled` bool (default true — the game cuts it when its electric feed is dead) | `detail.q_m3h`, coupling `p_el_kw` ≥ 0 (draws ρ·g·Q·H/η while pumping) |
  | `water_tower` | water | `volume_m3`, `tower_height_m` (the game adds it to the junction's `elevation_m` in `native` — the tank bottom sits at node elevation) | — (fills/drains via the backend's tank + pump-hysteresis machinery) | `soc` = level fraction, `detail.level_m` |

  Storage note (Phase 8, additive): `battery`, `storage_heat` and
  `water_tower` accept an OPTIONAL `soc` param (0..1, clamped) at
  `net/reset`/`add_device` — the initial state of charge / level fraction.
  Backends without a value keep their defaults (battery 0.5, heat storage
  0.0, tower 0.8). The game replays the last solved `soc` on every
  registration so topology resets and save/load preserve storage state.

  Water notes: the water `native` payload is rtwaterflow's five-file bundle
  (`network_structure` with per-junction `elevation_m`, `pipes` with explicit
  `inner_diameter_mm`/`k_mm`, `consumers`, `supply`, `environment`). Zones map
  by consumer NAME (like heat). `zone_demand.value` is m³/h. Zone detail is
  `{p_bar}`; `supplied` is the **Wagner PDD fraction** — low pressure yields
  weak taps before dry taps. Violation kind for water: `pressure_low`.
  A water network needs at least one pressure boundary (a `water_tower` or a
  `slack` external feed).

Response:

```json
{"ok": true, "network_kind": "power", "n_zones": 10, "n_devices": 4,
 "warmup_solve_ms": 3120.5, "warnings": []}
```

Errors (bad document): HTTP 400 with `{"detail": …}`. A reset clears `last_t`
(the next step may carry any `t` — the game clock continues across resets).

### 3.2 `POST /gb/net/patch`

Array of ops, tolerant per entry (applied ops stay applied even if later ops fail):

```json
[{"op": "add_device", "device": {"id": "gen2", "kind": "generator", "node": "b2", "params": {"p_max_kw": 300}}},
 {"op": "remove_device", "id": "gen1"},
 {"op": "set_device", "id": "pv1", "params": {"p_rated_kw": 250}}]
```

→ `{"applied": ["gen2", "gen1"], "errors": [{"index": 2, "error": "unknown device pv1"}]}`

v1 scope: device ops only. Node/edge/zone changes go through a full `reset`
(cheap at Phase 2–3 network sizes; diff-based patching is Phase 3 work).

## 4. Stepping

Request ([schemas/step-request.schema.json](schemas/step-request.schema.json)):

```json
{
  "t": 4711,
  "dt_s": 900,
  "weather": {"wind_ms": 6.2, "ghi_wm2": 410.0, "temp_c": 12.5},
  "zone_demand": {"z0": {"value": 120.5}},
  "device_setpoints": {"gen1": {"p_kw": 500.0}},
  "coupling_in": {"cpl_heat": {"p_kw": 80.0}}
}
```

- `zone_demand.value` unit by network kind: power kW(el), heat kW(th),
  water m³/h. Missing zone → backend holds the zone's previous value
  (sample-and-hold); zones never seen default to 0.
- Power note: zone demand is the SIGNED net load — negative means the zone
  exports (e.g. rooftop-PV backfeed through the district transformer). Heat
  and water zone demands stay non-negative (backends may clamp).
- `weather` is applied by backends that model weather-dependent physics
  (heat: outdoor temperature drives the heating curve / loss boundary);
  power ignores it (the game computes PV/wind availability itself and sends
  setpoints — generation *models* live game-side, network *physics* backend-side).
- `coupling_in` routes cross-network values onto `coupling_load` devices
  (power) — the orchestrator forwards `coupling_out` of network A at step
  `t−1` as `coupling_in` of network B at step `t` (ROADMAP §2.5, one-step-lag
  Gauss–Seidel).
- Setpoints/demands are clamped to device/physical bounds by the backend;
  clamping is reported as a `violation` of kind `"clamped"`, never an error.

Result ([schemas/step-result.schema.json](schemas/step-result.schema.json)):

```json
{
  "t": 4711,
  "status": "converged",
  "solve_ms": 14.2,
  "zones": {"z0": {"supplied": 1.0, "detail": {"v_pu": 0.984}}},
  "devices": {"gen1": {"output_kw": 500.0, "soc": null, "detail": {}}},
  "coupling_out": {"chp1": {"p_el_kw": -93.6}},
  "violations": [{"element": "line:2", "kind": "overload", "severity": "warning", "value": 104.2}]
}
```

- `status`: `"converged"` | `"degraded"` (solved via a fallback tier — heat's
  retry ladder) | `"failed"` (no solution — the game maps this to a
  blackout/supply-disturbance event for every zone of the network).
- `zones[].supplied` ∈ [0, 1]. v1 mapping: converged → 1.0 (with quality in
  `detail`: power `v_pu`; heat `t_supply_c`, `dp_bar`), failed → 0.0.
  Fractional values arrive with pressure-driven demand (water, Phase 5) and
  zone-level degradation (Phase 3+).
- **`edges` (optional, since 1.1):** per-edge solved quantities for map overlays —
  `{"edges": {"L0": {"loading_percent": 84.2, "p_from_kw": 120.3}, …}}`. Edge ids
  follow the native element order (`"L<idx>"` for power lines, `"T<idx>"` for
  transformers). Backends MAY omit the field entirely (a 1.0 consumer ignores it);
  the game's line-loading overlay consumes it.
- `violations[].severity`: `"info"` | `"warning"` | `"critical"`. v1 kinds:
  power `overload` (line/trafo loading %, warning > 100, critical > 120),
  `voltage` (vm_pu outside 0.95–1.05); heat `dp_low` (worst-point Δp below
  DP_MIN), `t_supply_low`; all: `clamped`.
- Out-of-order `t`: HTTP 409 / WS frame `{"t": …, "status": "error", "error": "out_of_order", "expected": [last_t, last_t+1]}`.
- `GET /gb/result/latest` → the last result (404 before the first step).
  Together with idempotent re-send this is the crash-recovery path.

## 5. Failure & recovery semantics (game side, normative)

- Backend process dies → SidecarManager restarts it; the orchestrator, on
  recovery, re-sends `reset` (topology from the game model — the model is the
  source of truth, ADR-002) and resumes stepping at the current game step.
  Steps missed while down are **skipped, not replayed**; the result cache
  interpolates and the affected zones raise a supply-disturbance event for the
  gap (ROADMAP §2.5: never stall the game loop).
- `status: "failed"` on N consecutive steps (N=3 default) escalates the event
  severity but keeps stepping — recovery is always attempted next step.

## 6. Versioning

Breaking changes bump MAJOR and get a new `docs/contract/v2.md`. Additive
fields bump MINOR here. Backends report their contract version in `/gb/version`;
this file is versioned per change in its header.
